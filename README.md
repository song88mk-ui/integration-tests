# Cross-repo contract tests

Tests the seams between the song88 service repos, which unit tests in any single repo cannot see.
Tracked in DEVOPS-409 and DEVOPS-444, under the integration test programme DEVOPS-413.

It tests what is deployed, not source: the images one environment runs, at the tags ArgoCD
pins. No service repo is cloned.

## Why

odds-engine-2, bet-genius, backoffice-final and platform-final share one RabbitMQ topic exchange,
`e.central`. Producer and consumer each hand-maintain their own class for the same message, and
every producer serializes with System.Text.Json default options (PascalCase CLR names, enums as
integers). If a field is renamed, retyped or never sent, the consumer silently deserializes a
default. No compiler, unit test or log line notices.

## Layers

| Layer | What it checks | Where |
|---|---|---|
| 1 Message contracts | Each producer's real publish path emits a golden payload. Each consumer deserializes it into its own class, and the test fails on any field left at its default. | `harness/` |
| 1b Routing topology | Every published routing key reaches a deployed consumer, and every binding has a publisher. Reads the publish sites in the image assemblies, the helmfile app lists, the argocd values and each image's `appsettings.json`. | `routing/` |

Layers 2 to 4 (shared DB schema, HTTP contracts, broker-in-the-loop) are planned in DEVOPS-413.

Emitter and checker projects are added to `harness/` one per image, for example
`Emit.OddsEngine` and `Check.Platform`. Each one sets `<ContractImage>` and imports
`ImageReferences.props`, which references every assembly in that image's `/app`. One test
project could not reference them all: the images carry EF Core 3.1, 5, 8 and 10, and .NET 8 and
10 builds of the same libraries.

## Run

```bash
scripts/ecr_login.sh dev       # once per 12 hours; see "ECR access" below
run.sh                         # dev; known defects reported, not gating
run.sh --env prd               # what prd runs
run.sh --include-known         # known defects that still fail also fail the run
run.sh --no-pull               # re-run on the images already extracted, offline
run.sh --tag oev2-sportsbook-service=sha-1234567-dev   # try another build of one image
```

It needs the .NET 10 SDK, [uv](https://docs.astral.sh/uv/), Docker (to pull the images, and
for the `mongo:8.0.13` container behind the Sportsbook settlement and bet-stop emitters), and
`gh` logged in to an account that can read `argocd` and `infrastructure`.

1. `scripts/pull_images.py` downloads `argocd` and `infrastructure` at `CONTRACT_CONFIG_REF`
   (default `main`) as GitHub tarballs into `.cache/config/`. From them it lists every app the
   environment deploys and the tag ArgoCD Image Updater pinned
   (`argocd/argocd-image-updater/<appsDir>/<app>/<env>.yaml`).
2. For each .NET image (prefixes `oev2-`, `bg-`, `backoffice-`, `platform-`, minus the
   non-.NET ones in `deployment.NON_DOTNET_IMAGES`) it pulls
   `<registry>/<image>:<tag>` for linux/amd64 from the ECR registry CI pushes that
   environment to (`CONTRACT_REGISTRY` overrides it), and
   copies `/app` into `.images/<env>/<image>/`. An image whose digest has not changed is not
   copied again.
3. It prints each image's tag and commit (the `org.opencontainers.image.revision` label). That
   header says exactly what was tested.

A tag argocd pins that is no longer in ECR (the lifecycle policy keeps the last 5 `-dev`
images) is reported and skipped; `test_every_deployed_dotnet_image_is_extracted` then fails on it.
Network calls time out and are retried twice.

## Routing topology

`routing/` checks e.central as deployed in the environment `run.sh --env` pulled. Nothing in it
is listed by hand except the accepted gaps.

- **Deployed services** come from the argocd-apps releases in
  `infrastructure/helmfile/helmfile.yaml.gotmpl` (`dev` installs the `*-dev` releases), with
  each app's argocd values files merged in the order the argocd-apps chart applies them. The
  effective `MessageBroker:RoutingKey` is the image's `appsettings.json` overlaid with the
  argocd `env` block (`A__B` is `A:B`). A service counts as a consumer when its entry assembly
  subscribes (`MessageReceived +=` or `Received +=`).
- **Published keys** come from `Scan.Assemblies`, which walks the IL of every first-party
  assembly in each image with a symbolic stack of strings. A key counts when it reaches a
  `Publish` / `CPublish` call or a `RoutingKey` setter. Constants are inlined by the compiler,
  so they resolve exactly; a local or field set to one value resolves too. Anything else (a
  parameter, a loop variable, a variable set on two branches) becomes `*`, one unknown word.
  `SCAN_TRACE=<part of Type.Method>` prints the stack at each instruction of matching methods.
- `test_every_published_key_reaches_a_consumer` and `test_every_binding_has_a_publisher` fail on
  any gap not in `known_gaps.yaml`, and on any entry there that is no longer a gap.
- Defects have their own tests, marked `@pytest.mark.xfail(reason="<ticket>")`: DEVOPS-416 and
  DEVOPS-440 today. `run.sh` reports one that starts passing as `NOW PASSES`, and
  `--include-known` runs them as ordinary tests (`pytest --runxfail`).

The deployment config is read at `CONTRACT_CONFIG_REF` (default `main`), so a run on a branch
of `argocd` tests that branch's app list and tags:

```bash
CONTRACT_CONFIG_REF=my-argocd-branch run.sh --env stg
```

## Writing an emitter

1. Drive the real producer code with a fake broker that records the payload, type and routing
   key (`Emit.OddsEngine/Fakes.cs`; the repos' own test fakes are in no image). Several
   OE payloads are anonymous types, so constructing a message class by hand would not test the
   wire. When the publish path needs a database, call the builder the publish path uses and
   say so in the test (`Emit.OddsEngine` reaches an `internal` builder by reflection).
2. Build the input with `SamplePopulator.Fill<T>()`, which gives every member a distinct,
   non-default value, then fix any field the producer parses or validates.
3. Run `DefaultValueScanner.Scan` on the produced payload and assert the exact list of fields
   the producer leaves default, each with a comment saying why. A consumer that reads one of
   those fields always gets a default, and its checker will say so.
4. Serialize with `ProducerJson.Serialize` (STJ default options, as every producer's broker
   does) and write it with `GoldenStore.Write(new Golden(routingKey, messageType, json))`.
5. When two producer paths publish the same routing key and type, give each golden a
   `Variant` (`OnBetSettlement~FromMarketSettlement.json`). Checkers read with
   `GoldenStore.ReadAll` and `ContractAssert.ForEachGolden`, so every variant is checked and a
   failure names the variant.
6. A publish path that reads the catalogue first gets a `MongoFixture` and seeds only the
   documents it reads (`Emit.OddsEngine/SportsbookServiceMongoEmitter.cs`).
7. Use `[GoldenFact]` and `[Trait("Category", "Emit")]`. `run.sh` runs every emitter before any
   checker.

Reference the producer's image by setting `<ContractImage>` and importing
`..\ImageReferences.props`. Add a harness project with
`dotnet sln harness/ContractTests.sln add --include-references false <project>`.

## Writing a checker

1. Use `[GoldenFact]`. It skips when `CONTRACT_GOLDEN_DIR` is unset.
2. Use `GoldenStore.FromEnvironment()!.ReadAll(routingKey, messageType)` and run the check
   inside `ContractAssert.ForEachGolden`, so every producer variant is checked. `ReadAll` throws
   when there is no golden, so a checker can never pass because the emitter stopped producing.
3. Deserialize with `ConsumerJson.Deserialize<T>`, the consumers' STJ defaults, which are
   case-sensitive. OE.Job.Cleanup and OE.Translation.Job set `PropertyNameCaseInsensitive`;
   pass their options.
4. `ContractAssert.NoDefaults(message, allowed: [...])`. It lists every default member, not the
   first five. Every entry in `allowed` needs a comment saying why that consumer field
   legitimately stays default (never read, or optional and guarded), and an entry that is no
   longer default fails as stale.

## Known defects

A checker that fails because of a filed defect uses `[KnownDefectFact("GM-902")]` instead of
`[GoldenFact]`, with the ticket key that tracks the fix. A fix that is deliberately deferred still
gets a backlog ticket to cite (GM-962, deferred in GM-959; decision in bet-genius
`docs/ArchitectureDecisions.md`).

- In a plain `dotnet test`, and in the gating pass of `run.sh`, it is skipped with the ticket
  key as the reason, so the suite stays green.
- `run.sh` then runs every known defect in a separate pass, one ticket at a time, and prints
  `still failing` or `NOW PASSES` for each. This pass does not fail the run. A ticket that now
  passes is listed again at the end. Confirm the fix is deployed, then change the attribute to
  `[GoldenFact]` so the test starts gating.
- `run.sh --include-known` makes a known defect that still fails also fail the run. Use it to
  confirm a fix.
- Run one ticket directly:

  ```bash
  CONTRACT_INCLUDE_KNOWN=1 CONTRACT_GOLDEN_DIR=goldens \
      dotnet test harness/ContractTests.sln --filter "Defect=GM-902"
  ```

  It reads the goldens from the last `run.sh`, so run that first.
